# REUSABLE MERN PRODUCTION IMPLEMENTATION RULES

This is a reusable implementation specification for building **complete, real-world, production-style MERN applications with Antigravity**.

These rules must be applied whenever an actual company/project implementation plan is provided.

---

# 1. MOST IMPORTANT RULE — PROJECT PLAN IS THE SOURCE OF TRUTH

The actual project implementation plan provided by the company determines:

**WHAT must be built.**

This reusable specification determines:

**HOW it must be built.**

The implementation plan may change from project to project.

Therefore:

```text
COMPANY PROJECT PLAN
        ↓
Understand requirements
        ↓
Identify required features
        ↓
Map features to architecture
        ↓
Implement complete functionality
        ↓
Apply these reusable development standards
        ↓
Test complete application
```

Do NOT use the same fixed feature set for every project.

Do NOT force Food Delivery features into a Travel application.

Do NOT force Travel features into an E-Commerce application.

Do NOT force unnecessary features into a project simply because they appear in this reusable specification.

---

3. Identify all user roles.

5. Identify all required pages.
6. Identify all required APIs.
7. Identify CRUD requirements.
8. Identify authentication requirements.
9. Identify authorization requirements.
10. Identify search requirements.
11. Identify filtering requirements.
12. Identify pagination requirements.
13. Identify image/file requirements.
14. Identify dashboard requirements.
15. Identify relationships between entities.
16. Identify frontend requirements.
17. Identify backend requirements.
18. Identify database requirements.
19. Identify validation requirements.
20. Identify error-handling requirements.
21. Identify deployment/environment requirements.

Create an internal requirement checklist before implementation.

Every applicable requirement must eventually be implemented.

# 4. NO STATIC OR MOCK APPLICATION

IMPORTANT:

The final application must NOT be a static demo.

Do NOT use fake project data as the primary application functionality.

Do NOT hardcode database records into React.

Do NOT create fake APIs that return static arrays.

Do NOT create buttons that do nothing.

Do NOT create forms that only display success messages without saving data.

Do NOT create dashboards using hardcoded statistics when those statistics should come from the database.

Do NOT stop after creating the UI.

The application must use:

```text
React
   ↓
Axios
   ↓
Express
   ↓
MongoDB
   ↓
Real database data
   ↓
React UI
```

If seed/demo data is required for development, it may be created separately, but the application itself must operate using the real backend/database.

# 8. REACT HOOKS

Use hooks where they solve real problems.

Applicable hooks include:

```text
useState
useEffect
useContext
useReducer
useMemo
useCallback
useRef
useNavigate
useParams
useLocation
useSearchParams
```

Do NOT artificially use every hook.

Each hook must have a meaningful purpose.

---

# 9. useState

Use `useState` for simple component state.

Examples:

```text
Form values
Search text
Loading
Error
Modal state
Selected item
Filter values
Pagination state
UI state
```

---

# 10. useEffect

Use `useEffect` for actual side effects.

Examples:

```text
Initial API requests
Authentication verification
Browser event listeners
External synchronization
Cleanup
```

Do not use `useEffect` for logic that can be handled directly inside an event handler.

---

# 11. useContext

Use Context API for genuine global/application state.

Examples:

```text
Authentication
Current user
Current role
Global application state
```

Possible structure:

```text
context/
├── AuthContext.jsx
└── AppContext.jsx
```

Authentication context may contain:

```text
user
role
isAuthenticated
loading
login()
logout()
```

---

# 12. useReducer

Use `useReducer` when multiple related state values need coordinated management in one place.

Example:

```js
const initialState = {
    loading: false,
    error: null,
    data: [],
    selectedItem: null
};
```

Use it for complex related state.

Do NOT use `useReducer` for every small state value.

---

# 13. useMemo

Use `useMemo` when there is meaningful expensive or repeated calculation.

Examples:

```text
Complex filtering
Derived statistics
Large calculations
Computed dashboard values
```

Do not use it unnecessarily.

---

# 14. useCallback

Use `useCallback` when stable function references provide a real benefit.

Examples:

```text
Callbacks passed to memoized children
Performance-sensitive handlers
Reusable callbacks
```

Do not wrap every function with `useCallback`.

---

# 15. useRef

Use `useRef` when a mutable reference or DOM reference is actually required.

Examples:

```text
File input
Input focus
DOM element
Previous value
```

# 17. ROLE-BASED ARCHITECTURE

If the project contains multiple roles, create separate role-specific structures.

For example:

```text

├── user/

├── restaurant/
└── deliveryPartner/
```

Only create roles that actually exist in the company project plan.

Do not invent roles.

# 18. PROTECTED ROUTES

Authenticated pages must not be publicly accessible when authentication is required.

Example:

```text
/login
/signup

/user/dashboard
/admin/dashboard
/restaurant/dashboard
```

The route protection must be connected to real authentication state.

Do not merely hide pages from the navigation menu.

Backend authorization must also protect the APIs.

# 19. AXIOS — API COMMUNICATION

IMPORTANT:

Do NOT use:

```js
fetch()
```

Use Axios for all frontend API communication.

Create centralized Axios configuration.

Example:

```text
services/
└── api.js
```

Example:

```js
const response = await axios.get(
    "http://localhost:3000/user/getUser",
    {
        withCredentials: true
    }
);
```

All API communication must use Axios.

---

# 20. HTTP-ONLY COOKIE AUTHENTICATION

When authentication is required:

```text
Login
   ↓
Backend validates credentials
   ↓
JWT generated
   ↓
JWT stored in HTTP-only cookie
   ↓
Browser automatically sends cookie
   ↓
Authentication middleware verifies JWT
```

Do not store authentication tokens in:

```text
localStorage
sessionStorage
```

when the project requires secure cookie-based authentication.

Use:

```text
withCredentials: true
```

where required.

---

```text
   ↓

   ↓

   ↓
```


Only implement additional authentication features if required by the project.

# 22. AUTHORIZATION

Authentication and authorization are different.

Authentication:

```text
Who are you?
```

Authorization:

```text
What are you allowed to do?
```

Implement role-based authorization when roles exist.

Example:

```text
user
admin
restaurant
deliveryPartner
```

Only create roles required by the project.

---

# 23. PASSWORD SECURITY

Never store plain-text passwords.

Use bcrypt or an equivalent secure password hashing mechanism.

```text
Password
   ↓
bcrypt hash
   ↓
MongoDB
```

During login:

```text
Entered password
       ↓
bcrypt compare
       ↓
Stored hash
```

# 29. HTTP STATUS CODES

Use proper status codes.

```text
200 → Successful GET / UPDATE
201 → Successful CREATE
204 → Successful DELETE with no response body
400 → Bad Request
401 → Authentication required / invalid authentication
403 → Authenticated but not authorized
404 → Resource or route not found
409 → Duplicate / conflict
422 → Validation error
500 → Internal server error
```

Do not return `200` for every situation.

Use status codes according to the actual result.

---

Create centralized error handling.

```text

 ↓

 ↓

 ↓

```

# 32. CONSISTENT API RESPONSES

Use a consistent response structure.

Example:

```json
{
    "success": true,
    "message": "User retrieved successfully",
    "data": {}
}
```

Error example:

```json
{
    "success": false,
    "message": "User not found"
}
```

Adapt the structure if the company implementation plan specifies a different response contract.

---

Validate:

```text

Password
IDs
Numbers
Enums
File requirements
Business rules
```

Do not trust frontend validation alone.

# 35. FILTERING

# 36. PAGINATION

Do not load large datasets unnecessarily.

Use backend pagination.

Example:

```text
GET /travel?page=1&limit=10
```

Backend:

```text
page = 1
limit = 10
skip = (page - 1) * limit
```

Response should include useful metadata when required:

```json
{
    "data": [],
    "pagination": {
        "currentPage": 1,
        "totalPages": 5,
        "totalItems": 50,
        "limit": 10
    }
}
```

Frontend should provide appropriate controls such as:

```text
Previous
1
2
3
4
Next
```

Do not load the entire dataset just to create pagination on the frontend when backend pagination is appropriate.

---

# 37. LAZY LOADING

Avoid loading unnecessary large amounts of data during application startup.

Load data based on:

```text
Current page
User activity
Selected resource
Pagination
Required dashboard information
```

Use React lazy loading/code splitting where appropriate:

```text
React.lazy()
Suspense
```

Do not lazy-load tiny components unnecessarily.

# 67. FINAL DEVELOPMENT PRINCIPLE

The goal is NOT:

```text
Use every technology.
```

The goal is:

```text
Build every required feature correctly.
```

The company implementation plan determines:

```text
WHAT
```

This reusable specification determines:

```text
HOW
```

The final application must be:

```text
Real
        ↓
Full-stack
        ↓
Database connected
        ↓
API connected
        ↓
Secure
        ↓
Validated
        ↓
Responsive
        ↓
Tested
        ↓
Maintainable
        ↓
Production-style
```

Never declare the project complete when it is only:

```text
Static UI
Mock data
Folder structure
Unconnected API
Placeholder buttons
Hardcoded dashboard
Fake CRUD
```

Build the complete application from the actual company implementation plan and adapt the architecture, models, pages, APIs, roles, business logic, and features to that plan.
